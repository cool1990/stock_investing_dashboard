## 0. 你的角色与目标

你是这个仓库的前端 + 数据工程师。目标是在 GitHub Pages 上实现一个静态网站中的「分析师预期」页面，第一只股票是美光（MU）。

页面要回答三个问题：
1. **市场现在预期什么**：未来各季度 / 财年的 EPS 与营收共识，和已公布值放在同一张表里比较，并给出增速和 Forward PE。
2. **预期在怎么变**：过去 90 天共识被上调还是下调、速度如何、是否已经消化公司指引。
3. **过去谁更准**：历史上分析师共识、公司指引与实际值之间的偏差。

**设计参考（务必先看）：**
- `docs/design/consensus-mockup.dc.html`：设计稿的完整源码，包括所有颜色、间距、字号和 MU 样例数据。它是设计工具专用的组件格式（`<x-dc>`、`{{ }}`、`<sc-for>`、`class Component extends DCLogic`），**不能直接运行**。请把它当作样式和数据的参考，用普通 HTML/TS 重新实现。`renderVals()` 里的计算逻辑可以直接参考。
- `docs/design/bloomberg-eeb-reference.png`：Bloomberg 的 EPS 预期页截图。「未来预期」区块的四宫格布局来自这里：左上是数值，右上是增速，左下是图，右下是估值。

## 1. 项目约束（不可违反）

- **部署**：GitHub Pages，纯静态。所有数据由 GitHub Actions 定时抓取，生成 JSON 并提交到仓库；浏览器端只读同源 JSON，**绝不在浏览器里直接请求第三方 API**（会遇到 CORS 问题，也不稳定）。
- **数据源**：必须免费、公开、尽量稳定。**不要用 Alpha Vantage。** 不需要 API key 的优先。
- **范围**：先只做美股；先做 MU，但所有代码必须按「多只股票」设计，股票通过 `config/companies/<TICKER>.yaml` 配置。
- **时效**：财报发布后 1 天内更新即可，不需要实时。
- **历史回填**：所有股票从**日历 2021 年 Q4** 开始。对 MU 来说就是从 FQ1-22（截至 2021-12 初）开始。
- **缺数据时**：显示 `[ ]` 或「不可得」，**禁止编造或插值**。页面上每个数字都必须能追溯到一个数据文件和一个来源。

## 3. 数据来源（逐项）

| 页面数据 | 主来源 | 获取方式 | 频率 | 备选 / 校验 |
|---|---|---|---|---|
| 未来季度 / 年度 EPS 共识（均值、最低、最高、机构数、去年同期） | Yahoo Finance | `yfinance.Ticker(t).earnings_estimate`，行为 `0q`、`+1q`、`0y`、`+1y` | 每日 | Nasdaq 分析师预测接口（见下） |
| 未来营收共识 | Yahoo | `Ticker.revenue_estimate`（同样四行） | 每日 | 同上 |
| EPS 共识的 7/30/60/90 天前取值 | Yahoo | `Ticker.eps_trend`（current、7daysAgo、30daysAgo、60daysAgo、90daysAgo） | 每日 | 自己的快照（积累 90 天后可以不再依赖 Yahoo） |
| 上调 / 下调家数 | Yahoo | `Ticker.eps_revisions`（upLast7days、upLast30days、downLast30days、downLast7Days） | 每日 | 无 |
| 营收共识的修正 | **免费源没有** | 用自己每日快照的差分来算；快照积累不够时显示「不可得」 | — | — |
| 已公布的调整后 EPS（逐季） | Yahoo | `Ticker.get_earnings_dates(limit=40)` 的 Reported EPS 列；`Ticker.earnings_history` | 财报后 | **公司新闻稿**（8-K EX-99.1），用 YAML 手工覆盖 |
| 已公布营收（逐季） | SEC EDGAR XBRL | `https://data.sec.gov/api/xbrl/companyconcept/CIK0000723125/us-gaap/Revenues.json`（MU 的 CIK 是 723125；概念名可能是 `RevenueFromContractWithCustomerExcludingAssessedTax`，两个都要试） | 财报后 | `Ticker.quarterly_income_stmt` |
| 历史「发布前共识」EPS | Yahoo | `get_earnings_dates` 的 EPS Estimate 列（可以回填到 2021） | 一次性回填 | MarketBeat 财报页（可能有反爬，失败就跳过）；**从现在开始用自己的快照** |
| 历史「发布前共识」营收 | 免费源很难回填 | 从现在开始用快照；历史部分手工补到 YAML，或者留空 | — | MarketBeat |
| 公司指引（下季营收 / EPS 区间等） | 公司新闻稿 | **手工录入** `config/companies/MU.yaml` 的 `guidance:`；以后可以考虑解析 EX-99.1 | 每季一次 | — |
| 股价、次日涨跌 | Yahoo | `Ticker.history(period="max")` 的日收盘价 | 每日 | Stooq CSV（`https://stooq.com/q/d/l/?s=mu.us&i=d`） |
| 下次财报日 | Yahoo | `get_earnings_dates` 中未来的那一行 | 每日 | 公司 IR 页手工填写 |

**Nasdaq 备选接口（需要你先验证是否可用）**：`https://api.nasdaq.com/api/analyst/MU/earnings-forecast`。据我所知它返回逐季和逐年的预测，必须带浏览器 `User-Agent` 头。它可能补上 Yahoo 拿不到的远期季度（见第 9 节）。如果接口不可用、或者结构变了，就记录日志并跳过，**不能让整个任务失败**。

**SEC 请求要求**：必须带 `User-Agent: "<项目名> <你的邮箱>"`，并且每秒不超过 10 次请求。

**关键：Yahoo 返回的是 `0q / +1q / 0y / +1y` 这样的相对标签，必须在抓取时立刻换算成绝对财期名**（FQ1-27、FY27），再写入快照。换算依据是 `MU.yaml` 的财季月份，加上 Yahoo 返回的 endDate（如果有的话）。财报发布后 Yahoo 会「滚动」：`0q` 从 FQ4-26 变成 FQ1-27。用相对标签存储会导致历史快照错位。

营收单位统一为**十亿美元**，保留两位小数；EPS 单位为美元/股。

### 4.3 `data/actuals/MU.json`

```json
{ "eps_basis": "non_gaap",
  "quarters": { "FQ1-25": {"eps": 1.79, "rev": 8.71, "release_date": "2024-12-18", "source": "yahoo|press"} },
  "years":    { "FY25": {"eps": 8.29, "rev": 37.38} } }
```

## 5. 计算口径（必须写单元测试）

| 项 | 定义 |
|---|---|
| 同比 YoY | 当期 ÷ 去年同期 − 1；年度行用上一财年 |
| 环比 PoP | 季度：当季 ÷ 上一季 − 1（Q1 对比上一财年的 Q4）；年度行与同比相同 |
| n.m. | **基数 ≤ 0，或当期 < 0** 时显示 `n.m.`；基数缺失时显示 `[ ]` |
| 增速格式 | 取整百分比，带符号：`+1003%`、`−13%`。负号用 Unicode `−`（U+2212），不用连字符 |
| 数值格式 | EPS 保留 2 位（`−1.91`）；营收用十亿美元、保留 2 位；表格内部不加 `$`，单位写在卡片标题 |
| 共识修正 | 当前共识 ÷ N 天前共识 − 1，保留 1 位小数 |
| 超预期 | 实际 ÷ 发布前共识 − 1 |
| 相对指引 | 实际 ÷ 指引中值 − 1；指引中值 = (低 + 高) / 2 |
| 发布前共识 | **发布时间点之前最近的一份快照**（MU 盘后发布，取发布当天的快照，如果当天快照是在发布后抓的，就取前一天）。快照不存在时回退到 Yahoo 的 EPS Estimate |
| 两源分歧 ⚠ | 两个来源的共识相差 > 3% 时，在历史表的共识单元格后加 ⚠，单元格变为琥珀色 `#9A6700`，悬停（`title`）显示两个值 |
| TTM EPS | 最近 4 个已公布季度之和（MU 在 FQ4-26 后 = FY26 = 75.52） |
| NTM EPS | 优先使用未来 4 季的共识之和；季度共识不全时用**时间加权**：`NTM = FY1 × (财年剩余月数 / 12) + FY2 × (1 − 剩余月数 / 12)`。在 JSON 里写明 `ntm_method`，页面脚注显示所用方法 |
| P/E | 股价 ÷ EPS 基数。EPS ≤ 0 时显示 `n.m.` |
| 相当于 TTM PE 的 | TTM EPS ÷ 该列 EPS（不需要股价也能算；FY27 = 75.52 / 156.53 = 48%） |
| 次日股价 | MU 盘后发布：T+1 收盘 ÷ T 收盘 − 1；盘前发布的公司：T 收盘 ÷ T−1 收盘 − 1 |

测试至少覆盖：MU 的 FY24 Q1（−0.95 对比 0.04 → n.m.）、FY25 全年（8.29 / 1.30 → +538%）、FY26 Q4 同比（+1003%）、FY24 Q3 环比（0.62 / 0.42 → +48%）。

## 9. 注意事项与坑（逐条处理）

1. **财期滚动**：Yahoo 在财报发布后 0–2 天内把 `0q` 滚到下一季。滚动前后两天的快照，财期名必须换算正确。写一个测试：给定一个日期和一个 Yahoo endDate，断言能得到正确的绝对财期。
2. **远期季度拿不到**：Yahoo 只有 `0q`、`+1q`，所以 FQ3/FQ4-27 的季度共识在免费源里通常没有 → 显示 `[ ]`；NTM 用时间加权（见第 5 节）。可以试 Nasdaq 接口补充，但不要依赖它。
3. **发布前共识**：必须在发布**之前**锁定。如果某一季缺少发布前快照，就回退到 Yahoo 的 EPS Estimate，并在数据里标记 `"pre_release_source": "yahoo_fallback"`。
4. **调整后 EPS**：XBRL 里只有 GAAP EPS。调整后 EPS 用 Yahoo 的 Reported EPS，并以新闻稿为准（不一致时用 YAML 的 `overrides` 覆盖）。FQ4-26 的 GAAP EPS 是 $32.87、Non-GAAP 是 $33.42，**页面统一使用 Non-GAAP**。
5. **年度 ≠ 四季之和**：见 4.3 节。
6. **单位**：Yahoo 的营收单位是美元，要换算成十亿美元；EPS 不需要换算。
7. **GitHub Actions**：cron 使用 UTC，并且可能延迟 10–30 分钟。建议设 `30 22 * * 1-5`（美东收盘后，北京时间次日 06:30），页面显示「数据更新 北京时间」。仓库 60 天没有活动时，计划任务会被暂停；每日 commit 可以避免这个问题。commit 时用 `github-actions[bot]`，并且只在数据有变化时才 commit。
8. **抓取的健壮性**：每个来源用独立的 try/except，失败时写入 `data/_status.json`（来源、时间、错误信息），页面「数据说明」读取这个文件。**某个来源失败时，保留上一份数据，不要用空数据覆盖**。yfinance 偶尔会被限流，加入重试（3 次，指数退避）。
9. **MarketBeat 和 Nasdaq** 这类非官方来源可能有反爬或改版。把它们放在 `fetch_secondary.py` 里，并且默认失败也无妨。
10. **GitHub Pages 的 base 路径**：Vite 的 `base` 设为 `/<repo>/`；前端用相对路径 `fetch('./data/pages/MU/consensus.json')`；部署时把 `data/` 复制到构建产物中。
11. **快照不可变**：`data/snapshots` 只追加，不修改。如果需要修正，写进 `overrides`。
12. **不要编造**：任何字段缺失都显示 `[ ]`。脚注和解读文字只能由数据推出。
13. **时区**：数据里的时间戳一律存 UTC，展示时转成北京时间。财报发布日按美东时间判断。
